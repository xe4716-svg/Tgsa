# 账号网关与登录保护：第二阶段

日期：2026-11-03。接续已通过 CI 的 `0d54f8f`，继续同一工程及 PR #27。

## 实际修改

- 复用 `public.account_gateway_leases`，没有新建第二套租约表或更改已发布迁移。
- 新增 GatewayLeases：按租户原子领取、续租、释放及 fenced_transaction。释放保留原行，重新领取递增 fencing_token，避免旧 Worker 使用同一计数复活。
- 领取和续租检查账号状态；冻结、撤销及暂停账号不能取得新的可用所有权。事务提交前再次检查真实数据库时间，租约到期则整笔回滚。
- 账号保存新增强制 family_id；在可能的租户/代理锁等待之后，锁定并复核租户状态、用户状态、成员写权限和仍有效的当前会话。提交前再次验证会话有效期。授权前记录网络风险同意也使用当前权限复核。
- 登录容量保护覆盖客户端创建中的请求和已登记流程，限制进程总数、单租户和单用户。取消或异常会释放预留；关闭 API 时取消尚在联网的申请并清除待授权连接。
- 网络调用设置超时；错误验证码和 2FA 尝试达到阈值后终止该流程。网络错误不伪装成密码错误，不回显内部信息。
- Telethon 禁用内部 FloodWait 睡眠，把服务端等待交给协调器；等待期间同一租户用户不能刷新 QR、重新申请验证码或继续提交凭据。HTTP 返回 429 和 Retry-After，明确剩余等待。
- 以上保护阈值通过 .env.runtime.example 中 TELEGRAM_LOGIN_* 环境变量设置，是技术保护阈值，不修改会员套餐额度。

## 实测覆盖

- 12 个并发领取者只有一个成功；续租、主动释放、过期接管、跨租户拒绝、旧 token 续租/释放/写入拒绝、冻结账号拒绝，以及租约在事务内过期后的数据回滚。
- 账号保存阻塞在真实代理行锁时，另一个事务将成员降为 VIEWER、移除成员、停用用户、撤销会话或让会话过期：五种情况下均拒绝写入，账号、协议号、代理绑定、同意记录与审计均无残留。
- 入站并发配额在网络调用之前生效；取消和退出释放资源；Telegram FloodWait 原值等待；错误验证码与 2FA 次数限制；网络错误脱敏。

实际计数见 docs/validation/gateway-results.json 和 gateway-*.xml。套件存在重叠，不相加作为独立覆盖率。外部 Telegram 调用仍使用模拟适配器，数据库测试使用真实 PostgreSQL 和受限 runtime。

## 仍需完成的边界

数据库租约和 fencing 不能自动取消已经发往 Telegram 的请求。此阶段没有实现并上线完整 MTProto 常驻连接运行器，也没有声称“真实连接绝不会重叠”。后续必须让连接运行器使用租约，续租失败立即停止新操作、断开连接，并对发送结果不确定的操作先对账。

当前登录流程及 FloodWait 截止时间仍驻留单一 API 进程；进程重启后不得宣称等待状态已持久化。持久账号网关还需接入登录路由、跨进程任务与限流、Session 导入/更新协调、连接健康检查及用户主动启动门禁。保留单实例限制，不绕过 Telegram 等待时间，不轮换账号或 IP。

此阶段未进行真实 Telegram/代理/支付联调，也没有生产部署或生产数据修改。完整产品尚未达到最终验收。
