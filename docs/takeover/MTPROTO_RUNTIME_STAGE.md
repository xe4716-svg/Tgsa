# MTProto 只读连接运行器：第三阶段

日期：2026-11-03。接续 `a0ceefe`，仍使用唯一主工程 Tgsa 和同一整合分支。

## 本轮实现

- 增加 GatewayRunner 与显式账号 Worker 入口 `python -m app.workers.mtproto`。
- 从既有 PostgreSQL 表取得租约；在租户上下文与 fencing 事务内读取账号、加密协议号和当前代理绑定。没有新建账号/会话/租约表，没有改变已发布 SQL。
- 解密协议号与代理凭据，核对网络模式及唯一有效绑定。缺失、失效或未知代理配置拒绝连接，不回退直连。
- 托管客户端禁用自动重连、RPC 自动重试及主动接收更新；只调用 connect、is_user_authorized、get_me 和 disconnect。此阶段没有发送、入群、历史下载或自动发布 API。
- 连接就绪前核对协议号真实账号 ID 与平台保存账号 ID；NEW_DEVICE 不会自动改为可发布状态。
- 心跳复核租约、账号状态以及协议号/代理/安全状态指纹。租约丢失、数据库检查失败、账号暂停或材料变化时，取消在途只读操作并断开。
- 正常关闭先断开 Telegram，再释放租约。无法确认断开时不提前释放；当前租约仍有效时暂停账号、写安全事件与审计，并抛出明确故障。旧租约无法更改新所有者状态。
- FloodWait 使用既有 lease_expires_at 保存至少覆盖服务端要求的等待截止时间，同时递增 fencing_token，使旧 Worker 不能续租或提前释放等待；同时保存安全事件与审计。等待不会因重建 Runner 实例而消失。
- 等待写入失败时返回 WAIT_PERSIST_FAILED；入口不自动重试、不配置自动重启，要求先处理该故障并遵守返回的等待时间。
- Worker 支持 SIGTERM/SIGINT，关闭数据库池；输出只有受控状态和等待秒数，不输出协议号、凭据或原始异常内容。

## 登录与网关交接修正

原流程在协议号入库时直接设置 AUTHORIZED，登录连接尚未确认断开前存在网关提前接管的窗口。本轮改为：

1. 账号/协议号/代理/同意/存储审计原子入库，账号保持 PENDING。
2. 原登录客户端确认断开。
3. 再次验证当前网站会话与权限，原子切换到 AUTHORIZED 并记录连接完成审计。

PENDING 不能取得网关租约。断开或最终激活失败不重复创建账号；原流程仍存活时，可安全重试断开/激活。进程重启或流程过期后仍不自动激活 PENDING，后续需完成受控恢复入口。

## 已执行验证

- 原有根工程单元与 PostgreSQL 回归保留。
- 模拟 Telethon：正常停止、续租失败、数据库失败、配置变化、连接关闭、身份无效/不符、FloodWait 持久化失败、断开异常、外部取消和连接中停止。
- 使用实际安装的 Telethon 构造托管客户端验证参数兼容，不联网。
- 真实 PostgreSQL + 受限 runtime：DIRECT/PROXY 的加密材料读取与代理解密；协议号/代理变化、账号暂停及代理失效后的停止；断开异常的暂停/告警/审计；持久等待阻止新实例领取，旧 fencing 无法提前结束等待；PENDING 交接门禁及幂等激活。
- 外部 Telegram 仍使用模拟适配器，不把上述测试描述成真实账号联调。

确切计数及时间见 `docs/validation/mtproto-results.json` 和 mtproto-*.xml。套件有重叠，不合计为独立覆盖率。

## 使用边界与后续门禁

本轮入口是显式选定账号的受控验证入口，不是最终多账号调度器，不新增微服务或自动扫描所有顾客协议号。API 登录仍在单实例内，跨进程登录调度与登录 FloodWait 持久化仍未接通；这里持久化的是已入库账号网关的服务端等待。

数据库 fencing 不能撤销已经发往 Telegram 的请求。网络分区、进程冻结和无法断开等边界仍需真实环境故障注入；不能声称绝对无连接重叠。旧 Worker 退出不明时，应由进程监管器终止旧进程，禁止直接重复启动同一账号。

后续还需：多账号任务注册/路由、持久登录命令、只读资产盘点、用户主动启动同步、Bot/MTProto 业务接通、历史/实时克隆、媒体引用与未知发送结果对账、真实代理/Telegram 联调和完整部署验收。没有生产部署或生产数据修改。
