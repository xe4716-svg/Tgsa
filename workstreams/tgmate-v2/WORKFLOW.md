# 开发与交付工作流

## 工作看板

待办 → 就绪 → 开发 → 验证 → 自审 → 用户审核 → 已完成。外部条件不足的卡片记为“外部依赖”，同时推进不依赖它的就绪任务。进行中任务默认不超过一个工作包，避免重复建设。恢复业务开发须由用户明确恢复。

每张卡片记录：目标行为、依赖、涉及文件、验收条件、数据迁移/回滚影响、验证证据和未验证项。具体首批卡片见BACKLOG.md。

## 单个工作包

1. 核对当前文件、既有设计和最近证据，排除重复模块。
2. 写明问题及验收条件，保持001～003原始SQL不变；新变更只追加迁移。
3. 完成接口/实现及必要文档，新增模块复用RLS、任务/outbox、额度和审计。
4. 执行与改动匹配的检查；数据库改动在隔离库实际执行，不能用解析替代。身份、队列、迁移、保留策略改动需相应失败/恢复场景。
5. 自审：需求覆盖、租户越权、秘密泄露、幂等、未知结果、权限变化、数据保留及部署影响。
6. 提交用户审核：说明行为变化、已执行检查、未执行联调、已知风险与交付文件。

## Git分支与评审（上传获批后执行）

main保存可审查基线；一个工作包使用feature/TGM-编号-主题或fix/TGM-编号-主题。通过PR评审后合并，不直接在main开发。当前尚无提交/remote，以上为待实施流程。

PR遵循模板，至少一名审核者检查；具体审核者由仓库负责人设置，不虚构CODEOWNERS。禁止把临时本地秘密传到PR、Issue或CI日志。提交文件按清单选择，不能对原工作区直接git add .。

## CI与证据

仓库已准备static-checks工作流：只读仓库权限、Python语法编译、SQL解析。配置参考actions/checkout与actions/setup-python官方说明；配置准备不等于GitHub运行成功。

数据库集成CI尚未配置；M1完成后再加入独立PostgreSQL服务、受限角色初始化及全量测试，禁止依赖开发机.local。届时单独设置必须通过的检查，静态CI绿色不得代表数据库或实网通过。

204项测试是当前本地基线快照，不是未来提交自动继承的结论；报告须绑定具体代码/SQL版本。真实Telegram联调单独标记，生产验收独立签字。

## 发布关口

本地工作包完成 → 全新环境重建/恢复 → 浏览器与故障演练 → 自审清单 → 用户审核 → 才允许GitHub上传或生产操作。GitHub上传和生产发布是不同授权，本次只准备上传候选。

备份、迁移演练、回滚与数据恢复必须有实际记录；不可逆迁移采用备份恢复/前滚修复，不能承诺通用自动回滚。生产Token/会话使用独立凭据，绝不复用测试数据库或私有开发密钥。
