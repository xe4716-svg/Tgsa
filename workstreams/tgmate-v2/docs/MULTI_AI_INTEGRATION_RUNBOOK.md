| `ai/10-devops-deploy` | Docker、CI、监控、备份恢复、部署文档 | 默认不部署；生产密钥只从 Secret Manager 注入 |

## 并行开发规则

1. 每项工作必须关联一个 GitHub Issue；Issue 写清目标、依赖、允许修改路径、禁止修改路径、验收标准和验证命令。
2. 每个 AI 只在其工作分支提交；不直接向 `main`、`integration/mvp` 或其他 AI 分支推送。
3. 跨模块改动先更新接口契约，再由集成负责人协调；不得各自复制一套 Telegram Identity、Session、代理、任务调度、会员权限或 outbox。
4. 每个工作包提交一个 Draft PR，目标分支为 `integration/mvp`；PR 必须说明已执行和未执行的验证。
5. 数据库迁移必须编号连续、可回滚策略明确、校验和稳定；不能把不同历史基线的同编号 SQL 直接覆盖。
6. CI 通过不等于真实数据库、Telegram 或支付联调通过。禁止在没有实测时写“已上线/已验证”。
7. 集成负责人按依赖顺序审核：身份/租户与数据模型 → 统一接口/任务调度 → Worker → 前端 → 端到端回归。
8. 只有用户审核通过后才合并到正式分支；部署另行审批。

## 统一架构约束

- 单一 Telegram Identity / Session / 代理出口管理中心。
- 单一任务注册、租约、状态与调度体系；不同执行通道隔离 Worker。
- 机器人群发与 Telegram 用户账号群发是两个独立发送通道，共用受控任务/审计基础设施。
- 机器人类别固定为五类：群发、群管理、双向、频道/群组克隆、贴纸克隆；账号群发不是第六种机器人。
- 会员权益由统一套餐/权限服务提供；各模块不得硬编码套餐额度。
- 所有租户数据必须按 tenant_id 隔离；敏感凭据不得进入日志、Issue、PR 或普通配置文件。
- Telegram 限流和账号安全优先于吞吐量；不通过轮换账号/IP 绕过平台限制。

## 需要实际接入的 AI 工具

GitHub 分支和 GitHub Actions 负责代码协作与自动测试，不会自行启动外部 AI 编程代理。Codex、Claude Code 或其他代理必须由仓库所有者分别完成授权/安装，授予最小必要的仓库权限，并配置其官方支持的任务触发方式。未完成授权前，只能称为“协作工作流已准备”，不能称为“多个 AI 正在并行开发”。
